# GMOコイン・レバレッジ取引ボット

対象はGMOコインの暗号資産レバレッジ取引です。`BTC_JPY`、`ETH_JPY`などを指定し、買い建玉と売り建玉の両方を扱います。既定はdry-runで、実注文は送信しません。現物ボットの状態ファイルとは銘柄名が異なるため混ざりませんが、旧現物版の状態をそのまま引き継ぐものではありません。

## 1. 設計方針

- **既定はdry-run**：公開APIのステータス、銘柄ルール、板、確定済み15分足を使い、仮想証拠金でシミュレーションします。
- **1時間周期・15分足**：全銘柄を1回ずつ処理した1時間後に次のサイクルを開始します。指標には既定で確定済み15分足を使い、未確定足は使いません。`KLINE_INTERVAL=1min`で従来の1分足へ戻せます。
- **EMA_RSI**：通常足の終値から短期EMA、長期EMA、RSIを計算します。BUYはゴールデンクロスまたは上昇トレンド中のRSI売られすぎ、SELLはデッドクロスまたはRSI買われすぎです。
- **HA_SMA**：SMAは通常足の終値で計算します。BUYはSMAゴールデンクロスと平均足の陽線が同時に成立した場合、SELLはSMAデッドクロスまたは平均足の陰線が既定2本連続した場合です。平均足は方向確認だけに使い、発注価格・数量・損益には使いません。
- **新規と決済を分離**：建玉がなければBUYまたはSELLで新規建玉を作ります。買い建玉はSELLで、売り建玉はBUYで建玉IDを指定して決済します。反対売買による即時ドテンは行わず、決済完了後のサイクルで次の新規判断をします。
- **含み益の順方向建玉は保持**：買い建玉で短期SMA／EMAが長期を上回る上昇傾向、または売り建玉で短期が長期を下回る下落傾向なら、手数料込み推定損益がプラスの間は通常の撤退シグナルで決済せず、利益を伸ばします。含み損の損切り、トレンド転換、－50円の強制決済は引き続き有効です。
- **追加建玉禁止**：同じ銘柄では方向に関係なく建玉1つ・pending注文1件だけです。liveでボット外の既存建玉を検出した銘柄でも新規注文を停止します。異なる銘柄は独立して処理できます。
- **最低単位が2,000円以上なら除外**：`TARGET_ORDER_NOTIONAL_JPY=500`を目標に数量刻みで丸めます。取引所の最低取引単位による約定代金が`MAX_ORDER_NOTIONAL_JPY=2000`以上なら、その銘柄では発注しません。最低単位が500円を超えても2,000円未満なら、その最低単位での発注を許可します。500円前後へ数量を刻める場合は従来どおり500円を目標にします。
- **－50円で強制決済**：決済側の最良気配と新規・決済手数料を含む推定損益が`ABSOLUTE_LOSS_CUTOFF_JPY=50`で設定した－50円以下なら、そのサイクルで即時決済注文を出します。スプレッド制限、クールダウン、日次損失停止より優先します。成行は使わず、買い建玉はbest_bidへの売り指値、売り建玉はbest_askでの買い戻し指値です。未完了注文がある場合は二重発注せず、照会・取消を優先します。
- **残高3,000円を保護**：「残高」は現物JPYではなくレバレッジ取引の取引余力です。liveは`account/margin`の`availableAmount`を使い、新規注文の概算必要証拠金（約定代金÷`LEVERAGE`）とtaker手数料相当額を差し引いた後も`MIN_REMAINING_BALANCE_JPY=3000`以上なければ発注しません。dry-runも同じ考え方で仮想取引余力を計算します。
- **動的な銘柄ルール**：各サイクルで公開`/v1/symbols`を読み、価格刻み、数量刻み、最小数量、maker/taker手数料へ反映します。`.env`の該当値はフォールバックです。
- **スプレッド**：`spread/mid`が`MAX_SPREAD_RATE`以上なら、そのサイクルは損切りを含めて発注しません。
- **指値**：通常BUYはbest_bid側、通常SELLはbest_ask側へ1ティック改善し、反対側の最良気配を跨ぎません。損切りは成行を使わず、買い建玉の決済はbest_bid、売り建玉の決済はbest_askの指値です。
- **注文管理**：前サイクルの注文を先に照会し、未約定分を取消します。最終状態と約定を確認するまで新規注文しません。新規live注文には`losscutPrice`も設定します。
- **リスク**：1取引の損失予算は評価資産の1%、日次損失停止は5%、最大建玉評価額は評価資産の10%です。複数銘柄のリスクは合計されます。日次判定には実現損益と含み損益を含む評価資産を使います。
- **安全性**：設定とAPIキーは同じフォルダの`.env`から必須で読み込み、OS環境変数より優先します。liveは`DRY_RUN=false`と確認文字列の両方を要求します。POSTの自動再送はせず、通信結果が不明なら`clientOrderId`で照会します。
- **監査**：`logs/bot.log`と日別CSVに、市況、指標、売買方向、新規／決済、注文、取消、約定、手数料、損益を記録します。

公式API仕様: <https://api.coin.z.com/docs/>

## 2. ファイル

- `GMO取引ボット_完全コード.txt` → `gmo_trading_bot.py`
- `GMO取引ボット_テストコード.txt` → `test_gmo_trading_bot.py`
- `GMO取引ボット_環境設定例.txt` → `.env`

3ファイルを同じフォルダに置いてください。`.env`は必須です。

## 3. セットアップ

Python 3.10以降を推奨します。

```bash
cd gmo-trading-bot
python3 -m venv .venv
source .venv/bin/activate
python -m pip install "requests>=2.32,<3" "python-dotenv>=1.0,<2"
```

dry-runではAPIキー不要です。live用のAPIキーには出金権限を与えず、必要な読み取り・レバレッジ注文権限だけに限定し、可能ならIP制限を設定してください。`.env`をGitへコミットしないでください。

対応する全レバレッジ銘柄の設定例です。現物銘柄は含めません。

```dotenv
SYMBOLS=BTC_JPY,ETH_JPY,BCH_JPY,LTC_JPY,XRP_JPY,DOT_JPY,ATOM_JPY,ADA_JPY,LINK_JPY,DOGE_JPY,SOL_JPY,SUI_JPY,MNT_JPY,BNB_JPY
LOOP_INTERVAL_SECONDS=3600
KLINE_INTERVAL=15min
TARGET_ORDER_NOTIONAL_JPY=500
MAX_ORDER_NOTIONAL_JPY=2000
MIN_REMAINING_BALANCE_JPY=3000
ABSOLUTE_LOSS_CUTOFF_JPY=50
LEVERAGE=2
```

状態ファイルは`data/state_BTC_JPY_dry-run.json`のように銘柄・モード別です。dry-runの`INITIAL_VIRTUAL_JPY`は銘柄ごとに用意されます。liveでは同一口座の取引余力を順次確認します。

## 4. dry-run検証

```bash
python -m unittest -v
python gmo_trading_bot.py --once
```

テストでは、認証署名、板、指値、RSI、SMA、平均足、15分足の未確定足除外、買い・売り建玉の損益、建玉ID指定決済、－50円ちょうどでの強制決済と他フィルターの優先、500円目標の数量、最低単位2,000円以上の銘柄除外、2,000円未満の最低単位での発注許可、注文後3,000円の余力条件、追加建玉禁止、日次停止、状態保存などを確認します。

`--once`で全銘柄を1回ずつ処理します。シグナルがない場合や、最低取引単位が2,000円以上の場合に注文が出ないのは正常です。CSVの`SKIP`と`result`に理由が記録されます。

継続実行と状態表示です。

```bash
python gmo_trading_bot.py
python gmo_trading_bot.py --show-state
```

dry-runを最初からやり直す場合は、停止後に対象の`data/state_銘柄_dry-run.json`だけを削除します。**liveの状態ファイルは削除しないでください。**

dry-runの約定モデルは、次サイクルの板で指値に到達したら全量約定とみなす簡易モデルです。待ち順、部分約定、1時間内の全値動き、強制ロスカットを正確には再現しないため、収益証明やバックテストとして使えません。

## 5. Private API認証だけを確認

`DRY_RUN=true`のままキーを設定し、次を実行します。取引余力を取得するだけで、注文は送信しません。

```bash
python gmo_trading_bot.py --check-private
```

ラズパイの時計をNTPで同期してください。署名時刻のずれは認証エラーになります。

## 6. liveへの切り替え

十分なdry-runの後にだけ設定します。

```dotenv
DRY_RUN=false
GMO_API_KEY=発行したキー
GMO_API_SECRET=発行したシークレット
LIVE_TRADING_ACK=I_UNDERSTAND_REAL_ORDERS
```

最初は1銘柄だけで`--once`を実行し、会員ページの注文・約定・建玉・取引余力とCSVを突き合わせてください。最低取引単位が2,000円以上の銘柄では実注文も出ません。

`--once`では発注後の注文を終了時に自動取消せず、次回実行で照会・取消します。継続実行を止める場合、既定では未約定の実注文へ取消要求を送りますが、停止後は会員ページでも確認してください。

## 7. 実運用前の必須確認

- `LEVERAGE`を口座の実レバレッジに合わせる。余力の概算と実際の拘束証拠金が異なる場合は発注が拒否されることがある。
- 最低取引単位が2,000円以上の銘柄は対象外。BTC_JPYなどで発注が出ない場合はエラーではなく保護動作。
- 取引余力3,000円の確保は証拠金維持率やロスカットを保証しない。レバレッジ取引では預入資産を超える損失や追加証拠金が発生し得る。
- 同一口座で手動注文や別ボットを併用しない。既存建玉を検出した銘柄は停止するが、口座全体の資金変動には影響される。
- 状態ファイルを削除・編集しない。別環境からの二重運用はロックで防げない。
- －50円の強制決済は1時間ごとの評価時点で動作し、常時監視ではない。指値が約しない間や急変時には損失が50円を超える可能性がある。`losscutPrice`を設定しても約定価格と損失額は保証されない。
- API障害、メンテナンス、部分約定、取消と約定の競合に備え、常に手動で停止・取消・決済できる状態にする。
- 本コードは教育・検証用であり、期待利益フィルターを通過しても利益は保証されない。
